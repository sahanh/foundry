# Apps — Start Here

> **Stub.** The server-side app guidelines are mostly unwritten — for now, [code-placement.md](../code-placement.md) is the source of truth for what belongs here and why. Two exceptions *are* written: **[transport-mapping.md](./transport-mapping.md)** (how a handler turns a domain outcome into a transport response — error shape, status mapping, and the pagination/filter/sort contract for collection endpoints), and the whole **frontend** subtree ([apps/web/](./web/start-here.md)).

`apps/` holds the **driving adapters** — the inbound entry points that call *into* the system. They come in two families:

- **Server-side transport** — HTTP/GraphQL controllers (`api/`), CLI commands, queue consumers/workers, MCP servers. Each is thin: parse/receive the transport request, call a service or orchestration, format the response. It imports `packages/core` (and any graduated `packages/*`) and holds no business rules. That last step — turning the outcome into a response — is the one translation it owns: see [transport-mapping.md](./transport-mapping.md), the edge application of the [error-handling strategy](../error-handling.md). **This file (and its [end-here.md](./end-here.md)) covers these.**
- **The frontend client UI** — the human-facing web app (`web/`). Also a driving adapter — it drives the system through the API — and also thin on business rules, but with a rich *internal* structure the transport apps don't have. **It has its own subtree: → [apps/web/start-here.md](./web/start-here.md).**

Each app is its own deployable unit with its own `src/`. The core never imports an app.

> **Which path is yours?** Doing **frontend/UI** work? Skip straight to **[apps/web/start-here.md](./web/start-here.md)** — the rest of this file is about server-side transport, so you can ignore it. Doing **backend transport** work (an HTTP route, a worker, a CLI, an MCP tool)? Stay here; you never need to open the `apps/web/` subtree.

**Content to follow (server-side transport).** Some of it is now written — **[transport-mapping.md](./transport-mapping.md)** covers how a handler maps a domain outcome to a transport response (the [error-handling strategy](../error-handling.md) applied at the edge: the response envelope, status mapping, and the pagination/filtering/sorting contract for collection endpoints). The rest will collect the driving-adapter guidance that currently lives scattered elsewhere — thin-controller rules, entry-point logging and trace-ID ingestion, "validation in integrators only," reusing the core's schemas at the boundary rather than redefining input shapes, and **authentication**: verifying the caller's credential and resolving a vendor-neutral **actor** onto `AppContext`. Authentication is an edge concern — the auth-provider SDK (Clerk, Cognito, BetterAuth, …) stays in the app; the app resolves the credential to an actor and sets `ctx.actor` before calling the domain, which then enforces authorization against it. See [identity-and-access.md](../packages/core/identity-and-access.md). That binding is **read-only** — the context asserts facts, it never establishes them ([app-context.md](../packages/core/app-context.md) → *The Context Is a Statement of Fact*); sign-up/provisioning is its own flow with its own trigger — see [identity-and-access.md](../packages/core/identity-and-access.md) → *Identity lifecycle*. In a **multi-tenant** app the edge does the parallel job for **tenancy**: it resolves which tenant the request runs within and sets `ctx.tenant` during the same assembly, so the domain runs already isolated. See [multi-tenancy.md](../packages/core/multi-tenancy.md).

When a change to a **server-side** app is complete, verify against [end-here.md](./end-here.md). A **frontend** change verifies against [apps/web/end-here.md](./web/end-here.md) instead. You are usually routed to the right one by the [review protocol](../review.md).
